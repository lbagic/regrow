# Architecture

Status: Phase 2 complete (execution, trash/undo, oplog, release pipeline); wedge features (Phase 3) next. This doc records structure and invariants; it grows with each phase. Product rationale lives in [PRODUCT.md](PRODUCT.md); build order in [PLAN.md](PLAN.md).

## Shape

Single static Go binary. Bubble Tea + Lip Gloss TUI. Rules are declarative YAML embedded at build time; code exists only for the weird cases (Docker df parsing, HF scan-cache, simctl).

```
cmd/regrow/        entrypoint, flag parsing, --json mode
internal/engine/   rule schema, loader, dry-run planner
internal/scanner/  size measurement, marker discovery, tool queries
internal/tui/      checklist UI, plan screen
internal/trash/    trash-not-rm + staging fallback, path guards, receipts
internal/oplog/    jsonl journal (grouping, undoable computation)
internal/executor/ runs plans across the trash/oplog seams; undo
internal/headroom/ free/purgeable/swap samples, history, forecast, alerts
internal/autopilot/ tick and prune: single flight, deferral, autotrim gate
internal/jsonl/    fresh-line appends shared by the oplog and headroom history
internal/protocol/ `regrow engine`: JSON lines over stdio for a shell app (docs/ENGINE.md)
rules/             *.yaml catalog (go:embed), --rules-dir override
```

## Data flow

scan → findings (semantic: what, why, regen story, cost, last-used) → user selection in TUI → **plan screen** (exact commands + trash destinations) → execute → oplog → undoable.

tick → sample (statfs free, purgeable, swap) → `headroom.jsonl` → forecast + crossings → alerts; with autotrim and low headroom, `PrunePlan` → the same executor → oplog.

## Invariants (the fence)

1. Dry-run is the default; execution is opt-in per run. One exception: autotrim (`regrow tick --autotrim`, the engine's `tick{autotrim}`) runs a rule's `prune:` policy with no per-run opt-in, only while headroom is low, and only once the oplog holds a completed manual `regrow prune <name> --yes` of that rule.
2. Nothing is ever `rm`'d directly: trash first, staging dir fallback, `--rm` explicit opt-out. One exception: a `prune` action deletes Go build cache entries unused for the rule's `min_age` directly, with no Trash and no undo; it is journaled with the files and bytes it deleted.
3. Every destructive path passes the guard: never empty, `/`, `$HOME`, or mount roots.
4. Native steward commands over raw deletion (`go clean -cache`, `ollama rm`, `docker builder prune`, `simctl runtime delete`). One exception: the go-build prune is a raw `/usr/bin/find <GOCACHE> -ignore_readdir_race … -delete`, because Go has no "trim entries older than" command. It deletes only the kind of file Go's own trim deletes (an `-a` or `-d` entry inside a two-hex-digit shard dir), and refuses unless `go env GOCACHE` names the directory, its README carries Go's cache header, and it sits on the volume whose free space was measured.
5. Risk classes are architectural, not cosmetic: `safe` (auto-clean), `caution` (review), `surface-only` (never deletable through us).
6. Every executed action lands in `~/.local/state/regrow/oplog.jsonl` before it runs.

## Testing

Fixture-$HOME builder + golden dry-run snapshots per rule. CI: macOS runner (Linux joins in v0.3). New rules ship behind `--beta-rules`.

- 2026-10-04 — the planner reads the containment forest (PR 1; shape pinned in the [attack plan](plans/2026-10-04-attack-plan.md)): an item's parent is the nearest item from any rule whose path strictly contains it, and on equal paths the later rule is the child. A selected item with a planned ancestor is skipped ("inside X, also selected", where X is the nearest ancestor whose action stays in the plan); an actionable item holding a surface-only item is refused ("contains Y, which regrow never deletes"), and so is one at the same path as a surface-only item of an earlier rule, which the parent rule alone would miss. A whole-rule command cannot leave items out, so it still runs while any of its items is outside other actions, and its bytes count only those items. Action bytes are therefore disjoint and `Plan.TotalBytes` is the union. Only a planned ancestor subsumes: a refused or unselected one does not.

- 2026-10-04 — a failed Empty Trash stops the run's Trash moves (PR 1 review): `osascript … empty trash` can fail (an Apple-event timeout on a large Trash) while Finder keeps emptying, so a later move could land in a Trash that is being destroyed. `Action` carries `empties_trash`; when such an action fails, the executor skips every remaining Trash move with a reason in `Result.Skipped`, and steward commands still run. Skipped actions are not journaled because nothing ran.
- 2026-10-04 — `regrow help`, `-h` and `--help` print the subcommand list and flags to stdout (PR 1, B8). Flags parse with `ContinueOnError`: an unknown flag returns an error that points at `regrow help` and exits 1.
- 2026-10-04 — every filesystem call of a scan is bounded (PR 2, B1; supersedes the root-only open probe): `open(2)` on another app's container can block forever without Full Disk Access, and a blocked syscall ignores ctx. `internal/scanner/walk.go` owns the bound. Tree walks (`DirSize`, discover, the ollama manifest walk) and single-directory listings (glob parents, the hf hub) run 4 workers under a watchdog: a directory with no progress for the stall window is written off, its worker abandoned and replaced, the walk marked partial; single calls (root `Lstat`, discover roots, the Docker VM disk stat) run on a side goroutine with the same rule. Progress is marked every 32 entries, after the visit has stat'd or read them, so a huge healthy listing or a visit that touches every entry is not mistaken for a blocked one. A cancelled scan blocks the calls it leaves in flight the same way, so a rescan does not join them. Two concurrent walks that reach one stuck path before either writes it off each leave a goroutine on it; that is bounded by the rules whose trees overlap there. The opener is injectable; tests block it at depth 3 and on a glob parent and assert the scan returns and a child process exits. A written-off call keeps its goroutine, so its path (and everything below it) stays blocked and is not touched again until that call answers: at most one stuck goroutine per path, however many scans the process runs, and a folder that starts answering (access granted) is read by the next scan.
- 2026-10-04 — a call is written off only when nothing else answers either (PR 2, measured): on the owner's machine the gated mediaanalysisd folder was not blocked for good; its open answered in 1.0–1.8 s on an idle disk and in 9–13 s while a full scan loaded the same disk. A flat 3 s deadline (the prototype's) reported it unreadable where the unbounded scan had measured 87 MiB. So the rule has two halves: the call made no progress for the stall window (5 s), and the walker as a whole got no answer in that window. Waiting for a slow call costs nothing while other walks still run; a folder that never answers ends the scan at most one stall window after the last useful answer.
- 2026-10-04 — `Usage` and `Item.Partial` (PR 2, B3; supersedes "2026-07-13 — `DirSize` never fails on walk errors"): `DirSize` returns `Usage{Bytes, Newest, Partial}` and its only error is ctx's. A target that refuses or blocks, root included, is an item with `Partial` set, shown as "unreadable" (nothing measured) or "≥ X" (a lower bound) with "blocked or unreadable (Full Disk Access may be needed)" — a likely cause, not a diagnosis. `Finding.Err` is left for rule-level failures: a tool error, an unknown query, a cancelled scan. Where the scan could not even enumerate (a glob parent, a folder under a discover root, the hf hub, an ollama manifest folder), the finding carries a pathless Partial marker item; without a path no plan can act on it. The planner is unchanged: `DefaultSelection` still takes a safe rule whose item is unreadable, and the plan shows it at 0 B.
- 2026-10-04 — last-used is the newest mtime over files and directories (PR 2, B4): the item root's own mtime said "unused 225d" for a cache written yesterday, and file times alone fail the other way (npm stamps 1985 on package files, only the directories carry the install time). `hf-hub` items take the same `Usage.Newest`; the earlier walk for blob atime through the snapshot symlinks is gone, so an hf repo's last-used is now its last download or refresh, not its last read.
- 2026-10-04 — `engine.Account` counts every byte once (PR 2, B2): `Ledger.Exclusive` is an item's bytes minus its direct children's in the planner's containment forest, floored at 0 (a partial parent, or a tree that grew between two walks, can measure smaller than a child). Each item's exclusive bytes land in one bucket derived from its rule, in this order: phantom-space category → macOS-managed, surface-only → shown only, steward command → frees now, otherwise → after Trash. Scan text, the TUI footer and `--json` show the four buckets instead of one sum (279.8 GiB claimed against ~164 GiB distinct in the blind review); category headers lost their totals because a category mixes buckets. `regrow scan --json` is now an object `{findings, totals, exclusive}`; `Totals` and `Ledger` gained snake_case JSON tags for it. What the forest cannot see stays double-counted across buckets, not within one: pathless tool items (docker objects live inside `Docker.raw`; purgeable space is mostly the aerial videos), which is why macOS-managed is its own bucket.
- 2026-10-04 — PR 1 review notes settled with the ledger (PR 2). Docker volume removals stay in "frees now", the bucket their steward command implies, and that overstates them: the pre-action writes an uncompressed tarball of the same size into staging on the same disk, and blocks freed inside the VM return to macOS only as `Docker.raw` trims. Both volume rules are caution, per-item and never default-selected; a "frees once staging is emptied" figure belongs with the staging view of PR 5. Nesting stays lexical (`filepath.Clean`): discover roots are now walked through a symlink, and hits are deduplicated by real path (the root's real path plus the hit's path below it), so a symlinked or nested root cannot report a directory twice and an inner root keeps hits deeper than the outer root's depth limit; two rules that spell one path in different case, or reach it through different symlinks, are still not recognised as nested — the catalog spells shared prefixes the same way, and the catalog test of PR 6 (one owner per byte) is the place to enforce it.
- 2026-10-04 — doctor verdicts are three-way (PR 2): flagged when the total, even as a lower bound, is over the line; normal when it is complete and at or under; unknown when it is partial (or the rule failed) and under. `HeroCheck.Verdict` replaces `Flagged`; before this an unreadable Spotlight index printed as a healthy 0 B.
- 2026-10-04 — `node-modules-dirs` `max_depth` 6 → 10 (PR 2, B6): on the owner's machine the rule found 32 directories at depth 6 and 64 at depth 10, the same set as a `find` with discover's excludes at depth 10 and at unlimited depth (deepest hit: 8).
- 2026-10-04 — docker build cache counts unshared records only (PR 2, B7): the rule claimed 1.6 GiB "unused 30d+" where `docker system df` said 0 B reclaimable, because every stale record was `Shared: true` — its bytes are an image layer's, and pruning the record frees nothing while the image stays. The classifier now skips shared records, as the daemon's RECLAIMABLE does; the query was wrong, not the label.
- 2026-10-04 — the parallel walker buys a full scan little (PR 2, measured on the owner's machine under a load average above 20): three alternating runs took 32–49 s before and 27–31 s after, and earlier pairs overlapped (41–62 s against 34–54 s); none hung. That is far from the 3.6× the walker gave a single tree, because rules already scanned NumCPU-wide and the kernel's metadata path was saturated before each tree got 4 workers. The time goes to walking shared subtrees twice (`~/Library/Caches` re-walks the go, yarn and brew caches); walking each subtree once is the next lever, not more workers.
- 2026-10-04 — tool queries have a deadline (PR 2 review): a wedged Docker VM or CoreSimulatorService leaves its CLI waiting on a socket forever, and the docker provider holds its lock while it waits, so every docker rule parked and the scan never returned. - 2026-10-04 — the go-build prune is the one sanctioned exception to invariants 1, 2 and 4 (PR 4, policy in the [direction doc](plans/2026-10-04-direction.md) D3). Go deletes cache entries only after 5 days unused and has no command to trim sooner, while worktree-heavy build bursts fill the disk within those 5 days. So the `prune:` block (`min_age`, `keep_under`, `unless_running`; validated: `go-build-cache` only, risk safe, `min_age` ≥ 1h, `keep_under` > 0) is planned by `engine.PrunePlan` as an ordinary `Action{Kind: prune}` and run by the ordinary executor. The planner walks the cache once into an hourly mtime histogram and takes whole hours, oldest first, until they hold `min(cache − keep_under, target − free)`, never an hour that ends after now − `min_age`; the last hour taken can carry the cache below `keep_under`, so it is "about" 15 GiB, not a floor. The command is `/usr/bin/find <GOCACHE> -ignore_readdir_race -mindepth 2 -maxdepth 2 -type f -path '<GOCACHE, glob-escaped>/[0123456789abcdef][0123456789abcdef]/*-[ad]' ! -newermt '<last second of that hour> UTC' -delete`: an absolute find; only shard dirs, as Go's trim and `go clean -cache` walk them, because a GOCACHE set to a shared dir such as `~/.cache` holds other tools' files that also end in `-a` or `-d` (the hex class is spelled out, since fnmatch ranges can follow locale collation); a UTC date the BSD find parses; and a cutoff on a second boundary, because find's sub-second handling of `-newermt` differs between builds. find re-stats every file, so an entry used after planning survives. Go refreshes an entry's mtime at most once an hour when it uses it, so "entries used in the last 48 h are spared" holds to within about an hour. The target bytes are fixed before anything runs; free space is not re-read while deleting, since Time Machine snapshots can hold freed blocks. The cache comes only from `go env GOCACHE` (run with `GOTOOLCHAIN=local`, so it never downloads a toolchain), symlinks resolved, path-guarded, and the README must start with Go's cache header; the executor checks the header again just before running. The executor measures the cache before and after and journals what was deleted on the done or fail line (`oplog.Pruned`); the start line carries the estimate. Single flight is a flock on `prune.state` in the state dir, which also keeps the deferral clocks. A running `go`, `compile` or `link` defers autotrim; regrow's own process and its ancestors do not count, so the `go` of `go run ./cmd/regrow …` is not a build. After 2 h of deferral, broken by any gap over 1 h between ticks (a sleeping laptop is not a running build), and with free space under 10 GiB, it prunes anyway, and the `min_age` cutoff still spares entries in use. The 1 h gap needs ticks at least hourly (the menubar ticks every 15 min); with rarer ticks the override never fires. A manual prune refuses while a build runs. `regrow tick --autotrim` refuses until the oplog holds a completed prune of the rule (`autopilot.Gate`), so "on only after one manual run" is enforced by data; a prune that ran to completion opens it even if it found nothing left to delete. A locked gate fails the tick only when headroom is low enough that a prune would have run; otherwise the tick succeeds and says autotrim is locked. A manual `--yes` that ends in a skip (nothing 48 h old right after `go clean -cache`, or a cache under `keep_under`) journals nothing, so it says the gate stays shut. A prune whose find fails fails the command (exit 1) from both `regrow prune` and `regrow tick --autotrim`. `regrow history` counts a prune by its measured bytes, not the start line's estimate. Known limit: the cache is found by running `go` from PATH, and an app launched by LaunchServices has no `go` on PATH, so the prune is refused there; the menubar shell (PR 5) must pass the login shell's environment to the engine or keep the verified GOCACHE.
- 2026-10-04 — headroom watch (PR 4): `internal/headroom` samples statfs free (`f_bavail`, what df shows; every threshold uses it), APFS purgeable (the JXA probe moved here from the scanner, which now calls it) and swap (`vm.swapusage`). Samples go to `headroom.jsonl` in the state dir, kept 30 days; it is not the oplog, so its reader skips malformed lines (a write cut short by a full disk) where the oplog's reader fails. Forecast: least-squares slope over at most 72 h of samples, restarting after any rise of 2 GiB or more (a clean says nothing about the trend after it); at least 3 samples over 3 h, and none while free space is flat or rising. Alerts fire on crossings only, each condition clearing past a wider line so a value hovering at one alerts once: free below 50/25/10/5 GiB (clears at the line + 10%, at least 1 GiB; one step across several lines reports the lowest), days-to-full under 3 (clears at 4), swap up ≥ 4 GiB within 30 min, free down > 5 GiB within 30 min. The two acute alerts name the process with the most resident memory. Known limit: the history file has no lock, so when two ticks run at once, one rewriting it to drop old samples can lose the other's sample. Autotrim prunes while free space is under 50 GiB or days-to-full is under 3, and its target is the larger of 50 GiB and the free space that gives 3 days at the forecast rate. `regrow tick [--autotrim] [--json]` prints one tick; `regrow prune go-build` is a dry run and `--yes` executes. The engine protocol's `tick{id, autotrim}` request (PR 3) is to call the same `Autopilot.Tick`.
- 2026-10-04 — a line cut short no longer locks the oplog (PR 4 review; amends the 2026-07-13 oplog protocol). Autotrim journals when the disk is nearly full, which is when a write can stop halfway. `Append` holds a flock on the journal from its check of the last byte through the sync, and starts on a fresh line when the file does not end in a newline, so two regrow processes journaling at once (`clean` and `tick --autotrim`) cannot glue a line onto the other's fragment. `Read` skips blank lines and a line that is the start of one entry and nothing else: it opens with `{"time":` (Time is the first field and never omitted) or is a prefix of that, the parser runs out of input with no other error, and no second `{"time":` appears in it, since a fragment followed by a whole entry can parse to the end the same way. Skipping such a line can miss a restore but never undo the wrong thing: a start line that failed to write refused its action, a lost done line drops its receipt, and a lost undo line leaves a receipt whose restore fails because the item is back. Any other unparseable line, garbage, zeros or two lines glued together, still fails loudly. Known limit: a cut right after a `\`, inside a `\u` escape, or inside a number or `true`/`false`/`null` ends in a different parser error and is not recognised, so that journal still fails loudly until the line is removed by hand; this costs availability, never safety. `internal/jsonl` holds the fresh-line rule both journals share; when the file cannot be read it assumes a fragment, since a spare newline is a blank line and a missing one glues two lines.
- 2026-10-04 — prune hardening (follow-up to PR 4). `-ignore_readdir_race` on the prune command: Go's own trim and `go clean -cache` (which removes whole shard dirs) can run while find walks, and without it a vanished shard or entry makes find exit 1, so the prune is journaled as failed and a first manual `--yes` leaves the autotrim gate shut although it deleted what it could. macOS find already only warns, exit 0, when an entry it is about to unlink is gone; the flag covers the walk. The cache must be on the volume whose free space was sampled (same `st_dev` as `headroom.Volume()`): a GOCACHE on an external disk would otherwise be trimmed again on every low-headroom tick while free space never moved. Another APFS volume in the same container shares its free space but has its own `st_dev`, so it is refused too; that is the safe side. `tick --autotrim` decides whether headroom is low before it reads the gate, so an oplog line `Read` rejects fails only the ticks that would prune and is reported, not failed, while free space is fine. When `headroom.jsonl` cannot be read the tick still samples and still autotrims, judging headroom by the 50 GiB band alone, with no forecast and no alerts; it says so and exits 1. The purgeable and `ps` probes get a 5 s `WaitDelay`, as the scanner's tool queries have, so a killed probe whose child holds its output pipe cannot block a tick. Known limit: deleted bytes are measured as the cache before minus after the command, so a build writing entries during a prune that overrode a build deferral makes the count low (floored at 0).
- 2026-10-04 — one owner per byte across the catalog (PR 6.1; settles the nesting note of PR 2): `internal/engine/catalog_test.go` fails when two rules name one path or discover one directory name. Paths are compared the way the filesystem compares them, case-folded (APFS) and with `/tmp`, `/var` and `/etc` read through `/private` on macOS, and a path inside another rule's path must spell the shared prefix the same way, because the containment forest compares bytes. The catalog passed with no exceptions. Tool-query items are outside its reach: their paths exist only at scan time.

- 2026-10-04 — the agent-session window is 24 h (PR 6.1): an ended session's scratch stays a day, long enough to pick the session up again the next morning, and a running session missing from the registry is offered only after a whole day without a change to its transcript or scratch. - 2026-10-04 — git worktree links keep a session (PR 6.1): a session whose scratch holds either end of a worktree link that leaves it stays kept, with "remove the worktree first": a `.git` file naming a git directory outside the session that exists (a worktree of a repository elsewhere, which belongs to the git-worktrees rule), or a repository whose `worktrees/<name>/gitdir` names an existing checkout outside (trashing it breaks that worktree). - 2026-10-04 — engine protocol (PR 3, contract in [ENGINE.md](ENGINE.md)): `regrow engine` serves one peer over stdin/stdout, one JSON object per line, every event naming the request it answers (`re`). One scan or execute in flight (`busy` otherwise); `plan` and `cancel` are answered meanwhile. A scan supersedes the previous scan's findings and plans when it starts, not when it finishes: a plan must never run against findings a running re-measurement is replacing. An execute spends its scan the same way: it drops every plan of that scan and later plans of it answer `scan_spent`, because a second plan would replay against findings the run changed (two plans that each empty the Trash would destroy the first run's moves). A plan id is single-use, expires after 10 minutes of wall-clock time (`Round(0)` drops the monotonic reading, which stops while a Mac sleeps), carries 128 random bits and is the oplog run id of its execution, so `regrow history` and `undo` reach engine runs unchanged. The engine executes on request: the shell's confirmation is the per-run opt-in (invariant 1), as `--yes` is for `regrow clean`.
- 2026-10-04 — one writer goroutine drains an unbounded event queue (PR 3). The attack plan said "a buffered channel"; any fixed buffer has to block or drop once full, and a blocked emit would stall the scan, the executor between actions, and the request loop that delivers `cancel`. The backlog is bounded by what the peer asked for (one finding per rule, two journal lines per action). A write error stops the writer and further events are discarded; shutdown waits up to 5 s for the queue to drain.
- 2026-10-04 — cancel and shutdown stop an execute between actions, never mid-action (PR 3): `Executor.Stop` is polled before each action and the engine never cancels the context it runs under. Killing a steward command midway leaves an action whose effect nobody knows; finishing it lets the journal say what happened. On stdin EOF, SIGINT or SIGTERM the engine cancels a scan, waits for an execute's current action and its journal lines, then exits; a second signal kills it.
- 2026-10-04 — the engine has no terminal (PR 3): `engine.PlanOptions{NoSudo: true}` turns every sudo action into a skip naming the `regrow clean <id>` to run in Terminal, decided before nesting so a refused sudo action never covers items nested inside it. The skip's command carries the engine's `--rules-dir` (made absolute) and `--beta-rules`, so Terminal loads the same catalog. `Action.Sudo` carries the rule's flag. The engine's `RunNative` gives steward commands `/dev/null` for stdin and captures stdout and stderr, whose last 4 KiB end the journaled error; it refuses `sudo` itself as defense in depth, and waits at most 10 s for output pipes a command's leftover daemon holds open. The docker volume export runs the same way with its stdout as the tarball, so a failed export journals docker's reason. SIGPIPE is caught with `signal.Notify`, not ignored: children inherit an ignored signal, and `yes | head` style commands would then fail loudly.
- 2026-10-04 — `hello.fda` is three-way (PR 3): `granted` when one entry of `~/.Trash` (else `~/Library/Safari`) reads, `denied` on a permission error, `unknown` when neither exists, the probe takes over 2 s, or the host is not macOS. Never an app container: opening one without Full Disk Access can block forever.
- 2026-10-04 — wire names (PR 3): `engine.Totals` and `executor.Result` gained snake_case JSON tags (`frees_now`, `after_trash`, `shown_only`, `macos_managed`, `partial`; `run_id`, `trash_bytes`, …) like every other serialized type; the pinned Totals shape named only the Go fields.
- 2026-10-04 — the engine bounds each Trash move at 60 s (PR 3 review): without Full Disk Access a Finder move or `Lstat` on a blocked folder can hang forever, and no cancel reaches a syscall. Known limit: the move is abandoned, not stopped. Its goroutine stays blocked, and a Finder move already requested may still land in the Trash, where Put Back restores it but `regrow undo` has no receipt. `regrow clean` keeps unbounded moves: it has a terminal, and Finder may be waiting on an authentication dialog there.
- 2026-10-04 — a last-used time outside JSON's years 0–9999 is cleared to unknown before a `finding` event is encoded (PR 3 review), and the engine plans from that same cleared finding, so peer and engine never disagree about a scan.
